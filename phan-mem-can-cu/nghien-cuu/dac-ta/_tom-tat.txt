SUMMARY: A .TMS file is a recorded copy of the same tab-separated command stream the program sends to the scale over TCP and RS-232. The tags are DWL (PC→scale data block), END, CLR (clear a whole table), UPL (PC asks the scale for data), ECS VER / END ECS (file header and trailer only) and LAE (end of one label block). Nothing in the decompiled code or install data writes or checks "XD1".

The PC export (SaveForm.cs:928-1239) writes a UTF-8 BOM, then an empty line, then "ECS\tVER\t100\t". Every record ends with a trailing tab and CRLF. =================== net-protocol [mostly-right] corrections=9 additions=18
SUMMARY: The network link carries plain TMS text, the same format as the USB file A_000.TMS. It is tab-separated, one record per line, ends every line with CRLF, and uses UTF-8 on this install. There is no binary framing, length field, command code, CRC or checksum, and no per-line ACK/NAK; TCP provides reliability.

The only code that touches the network is ECS\NetForm.cs. The scale is the TCP server on port 33581 (Spec43=1 server mode, Spec166). In client mode (Spec43=2) the scale connects to the PC on port 33582 instead.

Discovery uses UDP. The PC binds port 33584 and sends the 6 bytes "UDP\t\r\n" (hex 55 44 50 09 0D 0A) five times to 255.255.255.255:33583. The scale answers "UDP\t<tcpPort>\t..." to the PC's port 33584, and the PC then opens TCP to the sender's IP on that port. MAC, model and firmware are not in the UDP reply; they come over TCP.

On connect the PC writes an empty line (most likely preceded by a UTF-8 BOM, as .NET does). It then sends "UPL\tMAC\t" and gets the MAC back as six decimal bytes. Next it sends "UPL\tINF\t" and gets three lines: INF (shop, machine, number, model such as "TM-xA UA006 V3.14E8"), INA (encoding) and INM (hex MAC and which network interface, primary or secondary). It closes the exchange with "UPL\tEND\t". There is no login or password.

After that, the original program automatically pushes the PC clock with DWL TIM, pulls the sales logs, writes hidden Spec58=1 (asks the scale to announce new sales), and sends a "UPL\tTIM\t" link test every 30 s.

- **PC to scale:** blocks of "DWL\t<SEC>\t" rows then "END\t<SEC>\t". Sending "CLR\t<SEC>\t" plus "CLR\tEND\t" first erases that whole table. The scale sends nothing back. The PC ends every download with "UPL\tTIM\t" and waits up to 30 s for a line starting with END, which proves the scale has stored everything.
- **Scale to PC:** the PC sends "UPL\t<SEC>\t", the scale streams rows until a line starting with END, and the PC replies "UPL\tEND\t".
- **Sales logs:** "UPL\tREP\t[-]<first FID>\t" returns REP (receipt header), RES (item or payment lines) and REE (end of receipt). The PC asks twice and keeps the answer only when two reads agree. FID is the scale's receipt serial number, not a file id. "Success: N FID" in LogInfo.txt means N new receipts were imported in one pull.
- **Font, firmware and bitmaps:** binary is sent as text, one character per 4-bit nibble ('@' plus the nibble, high nibble first).
- **PLU line:** PLU plus 67 fields, which splits into 69 elements and confirms our tool's V3.14E8 layout. Prices use the "mantissa,decimals" format.

For our tool, the simplest upload is: open TCP to the scale on 33581, send an empty line, send only the needed sections (for example DWL PLU) from the edited file, and finish with the UPL TIM check.

SUMMARY: The label spec is written. A print format (tem) is one Label row plus 0–100 LabelItem rows. In a TMS file it is written as a LAB line, then its LAS lines, then LAE, all inside DWL LAB … END LAB.

**LAB line (confirmed):** `LAB, LabelID, Name, Sort, Width_mm, Height_mm, Text1..Text16, Version, Text17..Text32`, ending with a TAB (40 fields after split). Sources: SaveForm.cs:1097, NetForm.cs:3510, and the scale's own P26 menu in the V3.04A manual.

**LAS line (confirmed):** `LAS, SubID, Flag1, Flag2, Flag3, Print, Angle, Align, Font, Left, Top, Width, Height`, ending with a TAB.
- Left/Top/Width/Height are in dots (8 dots/mm), measured from the label's top-left corner.
- Angle rotates the box k×90° clockwise about (Left, Top).
- SubID (0–99) is the print order.

**Flag1 is the element type:** 0 Barcode, 1 Item, 2 Sale Info, 3 Const Text, 4 Outline Border, 5 Partition, 6 Bitmap, 7 Custom Print.
- For Item, the field is Flag3 (Name, Weight/Pcs, Unit Price, Shelf Date, Text1–7, and so on); Flag2 is the item index (0 = the current item).
- For Sale Info, the field is Flag2 (Print Date/Time, Grand Total 27, Store Name, …).
- For Const Text, Flag2 = n prints the label's Text(n+1).

**LAE** carries no data; it only closes each format.

**Which label prints:** if the PLU's LabelID1 (PLU line f[8]) is non-zero it is used, otherwise Spec000. When two or more items are accumulated, the sum format Spec005 is used instead. **Bitmaps:** stored on the PC in ECS.SBP, not in the database. They are converted to 1-bit by BitmapConvert.exe, packed with '@'-nibble encoding, and sent in their own `DWL BMP … END BMP` section. LAS rows only reference a bitmap by ID. Both installs' ECS.SBP files are empty.

=================== barcode-keys [mostly-right] corrections=7 additions=14
SUMMARY: I worked out both formats from the decompiled code, the shipped XML files, the DB dumps, the V3.04A manual and the CHM help, and checked them against each other.

**Barcode rows.** A BAR line is `BAR BarID Name Format Check Num1 Num2 TChar` with a trailing tab. The PC reads and writes it the same way (SaveForm.cs:1078, RDS.cs:933-955, NetForm.cs:3479).
- BarID 1..9 are factory barcodes, 10..99 are user barcodes, 0 is "System Default".
- TChar is a list of 6 to 32 elements. A numeric element is `<letters><length><shift><overflow>`, for example `B201` or `K500`. The letters are base-26 with A=0, so they cover 42 data sources (A..Z, then BA..BP).
- Some elements are not numeric: `>text\v` is constant text, `?nnn` is custom, `@gii` is a text field and `=gii` is a symbol. The symbols are loop markers, a checksum, or CRLF, and they are used to build QR codes that list every item of a sale (BarItemBox.cs:300-455).
- Shift drops that many digits from the right. Weight, money and count are turned into whole numbers using Spec208, Spec209 and Spec196 (factory values 3, 2 and 3).

**Barcode types.** Combo.xml gives: 0 Default (auto), 1 EAN13, 2 EAN8, 3 UPC-A, 4 UPC-E, 5 EAN-128C, 6 Code-128C, 7 ITF25, 8 PDF417, 9 EAN-128 (char), 10 Code-128 (char), 11 QR, 12 and 13 Code39, 14 Code93. There is no EAN-18 type. 18-digit barcodes are 17 data digits plus a check digit, printed as a Code-128 type.

**The "20 + 5-digit code + 5-digit value + check" layout.** Factory barcode ID 2 (`B201F501K500`) prints this with the total price, and it is already the factory default (Spec1=2, Spec2=20). For weight instead of price you need a user barcode 10..99 with `B201F501J500`. That is exactly what the vendor Wizard writes as ID 28 "QS-Item".

**How a PLU picks its barcode.** BarT1/BarT2 are the barcode number and BarF1/BarF2 the barcode flag, for Bill 1 and Bill 2. These are two separate printouts, for example a label on gap paper and a receipt on plain paper. They are not weighed-vs-counted and not front/back. A value of 0 falls back to Spec1/Spec2 for item labels and Spec6/Spec7 for sum labels. Class rows have the same six fields, and Spec54 decides which level wins. Right now every Beeftown PLU has 0, so the scale uses the factory default.

**Key lines.** An SCP line is `SCP PageID KeyID PLUID`.
- **Layers:** Page 0 is the first layer and page 1 is the Shift layer. The manual shows `scPLU 0-01` for key SC1 and `1-01` for Shift+SC1.
- **Key and PLU fields:** KeyID is the number printed on the key. PLUID is the PLU number, not the item code. A negative PLUID means a function key (-code). The manual only documents 0 as the first layer; that 1 is the Shift layer comes from its examples.
- **Face files:** each saved key map (a "face") has a layout and a page mode, but these only matter on the PC and are never sent to the scale. Only the face you select is exported.
- **Clearing keys:** in TMS and network exports, keys set to 0 are only written in "clear" mode. So to empty a key our tool must write an explicit 0 row.

**Keyboard models.**
| Model | Keys per layer |
|---|---|
| KA / KAB | 63 (numbered as a 5-column block then a 4-column block) |
| KAD | 40 |
| KB | 30 |
| KC | 40 |
| KD | 30 |
| KE | 10 |
| KF | 40 |

There can be up to 3 layers.

**Our tool's beliefs.** "Level 0 = first layer" is correct. KEY_LABELS is correct for the 63-key KA/KAB keyboards except key 58, which is `_` (underscore), not an em dash. The labels are wrong for the 40-, 30- and 10-key keyboards.

**Decoding for inventory.** Split the digits by the element lengths and verify the check digit. Then weight in kg = n/10^Spec208 and money = n×10^shift/10^Spec209. For Beeftown, which enters prices in thousands of VND, VND = money × 1000. With the factory Spec209=2, the 5-digit total field overflows at 1,000,000 VND. My reading of the overflow setting is that the barcode is then not printed at all, but this still needs a test print.
